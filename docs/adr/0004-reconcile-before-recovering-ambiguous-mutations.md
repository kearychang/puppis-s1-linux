# Reconcile before recovering ambiguous mutations

When a reversible device mutation has an ambiguous outcome, the application will not blindly resend it: it reconnects and compares observed state with both the requested state and the original snapshot, accepting the request or reporting no change when either matches. A mixed, unknown, or unreadable result triggers one restoration attempt; if restoration cannot be verified, the application enters recovery required and blocks further mutations, trading automatic retry convenience for protection against compounding an unknown device state. Secrets remain memory-only, so ordinary close is prevented after the mutation point, while a crash or power loss leaves a secret-free interrupted-operation marker and requires user-led reconciliation on the next launch rather than automatic password rollback. Recovery required clears only after the application verifies a coherent state and the user accepts it as the new baseline or completes a dedicated recovery transaction; restart and dismissal cannot clear it.
